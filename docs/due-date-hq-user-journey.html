Product skeleton

CPA 看到的是一张工作台，系统内部保留可审计的税务语义

最新设计不把 DueDateHQ 做成 landing page 或松散功能清单。第一屏就应该像一个可信的运营台： 日期、来源、状态、风险和下一步动作都靠近具体 deadline task。

视觉方向：light-first、dense、audit-friendly。使用明确 badges、紧凑表格、filter bar、evidence drawer 和 diff review，避免营销式大卡片、玻璃拟态、紫色渐变和含糊 AI 文案。
01 Firm

单用户 Beta workspace

CPA 注册、命名 workspace、选择主要服务 state，后续组织权限和邀请不进入 Beta。

02 Client relationship

个人与企业关系

CSV 可以提出关联建议，但不能自动 merge。CPA 确认 family、owner、business 等关系。

03 Filing / Tax profile

可匹配规则的 profile

entity type、jurisdiction、tax type、fiscal year、extension state 和 notes 进入 review。

04 Deadline task

带证据的工作项

official due date、firm target date、task status、verification badge 和 source evidence 分开展示。

第一问题：本周要做什么

默认 dashboard 直接进入 Due this week、This month、Long range，而不是先解释产品。

第二问题：为什么可信

每个 official task 都能打开 evidence drawer，看到 source、rule version、last verified 和 date history。

第三问题：哪里不能信

Needs review、Source changed、Unsupported、Coverage gap 和 User provided 必须可见，不能伪装成 Verified。

End-to-end journey

从首次登录到 dashboard triage，再到官方 notice diff 审批

每一步都写清 CPA 目标、系统反馈和信任边界。产品要让用户连续完成工作，而不是在 import、coverage、dashboard、notice 之间猜下一步。

旅程里的动词要具体：Review profiles、Apply selected updates、Reject selected updates、Decide later。不要暗示系统自动保证合规。
Step 01 注册与 workspace 初始化

CPA 想确认这是不是给自己用的工作台

邮箱密码注册后进入单用户 workspace，看到主要 state、服务类型和推荐导入路径。

Auth

系统给出一条最短起步路径

推荐 TaxDome / Drake / Karbon / QuickBooks CSV import，同时保留 manual entry 入口。

信任边界

此时没有 official task。页面只说明数据进入方式、coverage matrix 和 Verified rule 的含义。

Step 02 CSV 或 manual client capture

CPA 不想从零录入 30 个 clients

上传 source CSV 或手动创建 client relationship、filing/tax profile、state、entity type、fiscal year。

Import

系统先预览，不直接提交

adapter profile 自动识别 client name、EIN、state、entity type；低置信字段进入 review。

信任边界

CSV 来源不是税务来源。import 只能建立 profile 候选，不能自己产生 verified due date。

Step 03 Import review 与 relationship suggestions

CPA 要快速处理例外，不被整批阻塞

review rows 按 problem type 分组：missing EIN、ambiguous state、duplicate candidate、relationship suggestion。

Needs review

系统把 ready 和 review 分开

Ready profiles 可提交；uncertain profiles 停留在 review queue；relationship suggestions 必须由 CPA 确认。

信任边界

不能自动 merge 个体和企业关系。不能把 fuzzy inference 写成确定事实。

Step 04 Coverage matrix 与 obligation mapping

CPA 想知道哪些税类被覆盖

系统按 jurisdiction、tax category、entity type 显示 Verified、Needs review、Source changed、Unsupported、Coverage gap。

Coverage gap

系统解释能做什么和不能做什么

Ready profiles 匹配 obligation library。缺口可 request verification、add user-provided deadline 或 dismiss for now。

信任边界

Coverage gap 要可操作，但不能生成 official confirmed deadline。Unsupported 也不能被弱化成普通 warning。

Step 05 Generate deadline tasks

CPA 需要全年 calendar，但只接受可信日期

提交 ready profiles 后，Verified rules 立即创建 full-year official tasks。profile-level gaps 继续留在 review summary。

Verified

系统保留 date history

task 记录 official due date、original due date、optional firm target date、extension state 和 source evidence。

信任边界

Firm target date 是计划字段，不替代 official due date。User-provided deadline 必须标注 not verified by DueDateHQ。

Step 06 Dashboard

CPA 登录后 30 秒内要看到本周所有行动

默认分区是 Due this week、This month、Long range。行内展示 countdown、client/profile、state、task status 和 trust badge。

Dashboard

系统支持快速过滤和轻量批量动作

按 client、state、obligation、entity type、tax type、task status、verification status 过滤，目标 < 1 second。

信任边界

可批量更新 task status、firm target date 和 current-filter export。不能批量编辑 official due date。

Step 07 Evidence drawer 与 Source changed

CPA 要知道日期从哪里来

点击 evidence action 打开 drawer，查看 official source link、rule version、last checked、last verified 和 date event history。

Source changed

系统把来源变化推到 review

monitor 发现 source changed 后，相关 rule 进入 verification queue，新发布前不自动改变 workspace state。

信任边界

Source changed 不是新 official date。必须 review 并发布 rule version 后，才能影响后续 official tasks。

Step 08 Official notice proposal review

CPA 只想看可能影响自己 workspace 的变化

notice inbox 显示 P0 source allowlist 的检测结果，notice detail 在前，affected task/profile diffs 在后。

Review proposal

系统提出变更，不替 CPA 做决定

proposal 可以是 task update 或 coverage/review status update。CPA 逐条 approve、reject 或 decide later。

信任边界

AI 只做 notice 摘要和匹配建议，默认不发送 customer PII，不自动 mutate workspace data，所有决定进入 audit log。

Step 09 Feature progress 与 reviewer confidence

团队要知道 Beta 哪些部分可用

feature progress page 按 Auth、CSV imports、Manual entry、Tax obligation library、Monitoring、Dashboard、Deployment 等分组。

Progress

系统用稳定状态语言

每组只使用 Done、In progress、Blocked、Not started，并链接到对应 specs、环境和验证结果。

信任边界

progress 不是营销页。它说明产品 readiness、blocked reason 和下一步检查，而不是承诺已经 fully covered。

Screen inventory

关键屏幕必须服务旅程中的决策点

最新设计强调操作密度和状态可见性。每个屏幕都应该回答 CPA 当下的问题，并把证据、例外和动作放在同一上下文里。

Beta 第一屏不是宣传页。用户登录后应该进入 dashboard triage 或明确的 import setup，而不是需要先阅读功能说明。

TaxDome、Drake、Karbon、QuickBooks client/profile source intake。

Client relationship and filing profile setup

manual entry fallback for clients, profiles, and custom deadlines。

Manual entry

Dashboard

主要日常工作面，服务 filing-season morning。

Operational view
  • CPA question今天、本周、本月哪些 deadline 需要行动？
  • Primary controlshorizon tabs、filters、sort、one-click status、bulk status、bulk firm target date、export current view。
  • Trust cueverified badge 和 evidence action 在 deadline row 内显示。

Evidence drawer

官方来源证据要靠近 deadline task。

Evidence
  • CPA question这个 date 为什么存在？source 最近什么时候检查过？
  • Primary controlsopen source、view rule version、view date history、request review。
  • Trust cueofficial due date、original due date 和 firm target date 分列。

Coverage matrix

把 supported、unsupported 和 gaps 做成可行动列表。

Coverage
  • CPA question我服务的 state 和 tax category 哪些被 DueDateHQ 覆盖？
  • Primary controlsfilter by state/category/entity type、request verification、add user-provided deadline、dismiss for now。
  • Trust cueCoverage gap 不生成 official task，但必须保持可见。

Official notice inbox and proposal diff

notice detail first, affected item diffs second。

CPA approval
  • CPA question这个官方变化是否影响我的 clients？我应该应用哪些更新？
  • Primary controlsreview notice、compare before/after、approve、reject、decide later、bulk selected updates。
  • Trust cuemonitor 可以提出 proposal，但不自动改变 workspace。

Trust taxonomy

信任状态决定系统能不能生成或改变 official task

所有状态都必须带文字标签，不只靠颜色。用户要能从状态上判断：这是官方 verified 日期、需要 review 的候选项、覆盖缺口，还是自己临时录入的工作。

最重要的不变量：unverified data 永远不能用 Verified styling，firm target date 永远不能覆盖 official due date。
Status 用户看到什么 系统可以做什么 下一步动作
Verified official due date、source evidence、rule version、last verified。 创建 official system-generated deadline task。 Open evidence、mark task status、set firm target date、export view。
Needs review 匹配不确定或新 rule candidate，需要内部 review。 展示候选和影响范围，不能生成 official task。 Request DueDateHQ verification 或 add user-provided deadline。
Source changed 官方来源发生变化，现有信任需要复核。 创建 review queue item 和 notice proposal，不自动发布。 Review source diff、approve/reject proposal、publish new rule version。
Coverage gap 当前 jurisdiction/category/profile 没有覆盖。 显示 gap 和可选行动，不能创建 official confirmed deadline。 Request verification、add user-provided deadline、dismiss for now。
Unsupported Beta 明确不支持该 city、county、industry 或特殊 obligation。 保留 profile context 和说明，不生成 official task。 Manual tracking or ignore，避免误导成即将覆盖。
User provided 用户自行录入的 one-time 或 recurring deadline。 展示在 dashboard，允许 status/target date/export。 Request DueDateHQ review，不显示为 verified。
Firm target date firm 内部计划日期，与 official due date 分列。 用于排序、bulk update 和 workload planning。 Edit target date，但不能改写 official due date。

Official notice monitor

监控系统负责发现和解释，CPA 负责批准变更

官方 source monitor 是 DueDateHQ 的信任层，不是自动改账层。Beta 的 notice UI 要清楚显示来源、confidence gate、affected items 和每条 proposal 的决策状态。

P0 allowlist：IRS、California FTB、New York Tax Department、Texas Comptroller、Florida Department of Revenue。通知只在产品内展示，不承诺 email、SMS、Slack 或 calendar push。
01 Detect

24h source check

监控 supported official sources，发现可能影响 deadline 或 coverage 的变化。

02 Summarize

Explainable confidence

high/medium 进入 CPA-facing alert，medium 标注 AI-detected / needs review。

03 Match

Workspace impact

匹配本 workspace 的 profiles/tasks，默认不发送 customer PII 给模型。

04 Propose

Before/after diff

proposal 可更新 task 或 coverage/review status，界面必须不只依赖颜色表达 diff。

05 Decide

CPA approval

approve、reject、decide later 都进入 audit log，monitor 不自动 mutate workspace。

Beta scope

旅程必须诚实表达 Beta 的承诺和不承诺

DueDateHQ 要达到 File In Time 核心工作流 parity or better，但不是桌面软件克隆。Better 的部分来自 cloud workflow、verified source evidence、coverage visibility 和 no manual rollover。

产品语言要避免 “fully compliant”、 “guaranteed deadline”、 “AI handled it”。用可审计事实说明状态和下一步。

Beta 必须覆盖

  • Email/password registration and login。
  • TaxDome、Drake、Karbon、QuickBooks CSV import。
  • Manual client/profile/deadline entry。
  • Verified rules generate official deadline tasks。
  • Coverage matrix、verification queue、official source monitoring。
  • dashboard triage、fast filters、deterministic priority sort、dashboard export。
  • Feature progress page 和 Cloudflare deployment visibility。

Beta 先不承诺

  • 完整 50-state verified coverage 或税务责任保证。
  • 自动发布 rule changes 或自动改变 workspace。
  • 默认把 customer PII 发给 AI model。
  • client portal、document upload、e-signature、direct client notifications。
  • email、SMS、Slack、calendar push reminders。
  • bulk official due-date edits。

不是 File In Time 桌面克隆

  • 不复制 local database administration、backup/restore UI。
  • 不做 Crystal Reports-style reports、mail merge、labels。
  • 不做 arbitrary field renaming、network-user maintenance、detailed rights matrices。
  • 保留核心工作流：client setup、obligation setup、task generation、triage、filters、extension status、exports、urgency surfaces。

Success criteria

旅程评审时用这些结果判断页面是否讲对了产品

如果评审者看完页面仍然分不清 official due date、firm target date、coverage gap 和 user-provided deadline，说明页面还不够 DueDateHQ。

成功不是 “页面看起来完整”，而是 CPA 在几秒内理解哪些工作可信、哪些工作需要 review、哪些变更需要自己批准。
30 sec 登录后看到本周所有需要行动的 deadlines。
5 min 完成 weekly triage，替代 30-45 分钟 spreadsheet/calendar workflow。
P95 30 min 从 TaxDome 导入 30 clients，Drake/Karbon/QuickBooks 同样支持代表性 CSV adapters。
< 1 sec Beta-sized solo CPA workspace 的核心 dashboard filters 响应目标。

Final product check

这条旅程的核心判断

DueDateHQ 应该让 CPA 从 import 或 manual entry 开始，建立 client relationships 和 filing/tax profiles； 只用 Verified tax rules 生成 official deadline tasks；在 dashboard triage 中集中处理本周、本月和 long-range 工作； 在 evidence drawer、coverage matrix 和 official notice proposal review 中持续说明日期为什么可信、哪里不能信、哪些变更必须由 CPA 批准。
